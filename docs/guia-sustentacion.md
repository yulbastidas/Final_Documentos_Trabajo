# Guía de estudio y sustentación de SecureDocs

## 1. Cómo funciona la aplicación

SecureDocs permite guardar y consultar documentos según el rol, la propiedad y la clasificación de cada archivo. La interfaz real está en http://localhost:8080/portal. Desde allí puedes iniciar sesión, configurar MFA, cargar o descargar documentos según tus permisos y, si eres administrador, consultar usuarios, auditoría y reportes. La ruta /dashboard conserva la demostración con datos ficticios.

El recorrido de una solicitud es **navegador → Nginx → Next.js o NestJS → MySQL y almacenamiento privado**. Nginx sirve la interfaz y redirige las rutas /api/ al backend bajo el mismo origen. Next.js presenta los datos y envía solicitudes. NestJS aplica las reglas, MySQL conserva usuarios, sesiones, metadatos y auditoría, y el volumen privado guarda los archivos cifrados. Docker Compose conecta los servicios, aplica las migraciones y verifica su disponibilidad. Solo Nginx publica un puerto en el equipo local.

1. **Ingreso.** El portal envía correo y contraseña. El servidor verifica el hash. Si MFA está habilitado, emite un desafío y espera un código TOTP o de recuperación. Solo después crea la sesión.
2. **Sesión.** El navegador recibe una cookie HttpOnly. Al recargar, el portal consulta GET /auth/session. La API devuelve el usuario, sus permisos y el token CSRF. La interfaz mantiene CSRF en memoria y lo adjunta a las operaciones que modifican datos.
3. **Carga.** La interfaz envía el archivo, título y clasificación en multipart. La API comprueba sesión, permiso, CSRF, tamaño y tipo real. Si acepta el archivo, lo cifra, guarda el bloque cifrado en el volumen y registra los metadatos en MySQL.
4. **Descarga.** La API verifica el rol y la relación con ese documento antes de leerlo. Recupera la clave del archivo, verifica el cifrado autenticado y comprueba la huella. Entrega el binario como archivo adjunto.
5. **Auditoría y salida.** La API registra eventos permitidos, denegados o fallidos. El administrador consulta la actividad y los reportes. Cerrar sesión revoca el registro de sesión en el servidor y elimina la cookie.

### Demostración para el profesor

1. Inicia sesión con la cuenta administradora local. Abre Documentos y descarga la muestra interna.
2. Sube un TXT sintético marcado como restringido. Abre su detalle y muestra la huella SHA-256. Explica que la huella permite comprobar integridad y que el cifrado protege el contenido.
3. Cierra sesión y entra con la cuenta lectora. Descarga la muestra interna. La muestra restringida queda fuera de sus resultados. La prueba directa de descarga devuelve 404 para ese documento.
4. Vuelve como administrador y abre Auditoría y Reportes. Relaciona los eventos de carga y descarga con las acciones anteriores.
5. En Mi seguridad puedes demostrar el enrolamiento TOTP con una cuenta de prueba. Guarda los códigos de recuperación antes de cerrar sesión y evita mostrar la clave o los códigos en la exposición.

## 3. Preguntas que puede hacer el profesor

**¿Por qué usas hash y cifrado?** La contraseña solo necesita verificarse y se guarda como hash Argon2id. El documento tiene que recuperarse, por eso se cifra con AES-GCM. SHA-256 es la huella del documento y permite comprobar que coincide con el original esperado.

**¿Dónde queda la contraseña cuando inicio sesión?** Viaja al backend durante el ingreso, protegida por TLS en el perfil HTTPS. La API verifica el hash y emite una cookie de sesión. La base conserva el hash de la contraseña. La aplicación no coloca el token de sesión en localStorage.

**¿Qué pasa si copio el UUID de un documento restringido?** La ruta vuelve a validar permisos en el servidor. Para un lector sin visibilidad, responde 404. Ocultar un botón solo mejora la interfaz. La decisión de seguridad está en el backend.

**¿Por qué dos claves para documentos?** La DEK cifra un archivo. La KEK permite recuperar la DEK y se mantiene separada de MySQL. Un respaldo con el archivo cifrado y la base todavía necesita la KEK correcta para recuperar el contenido.

**¿Qué pasa si roban MySQL?** La base contiene hashes, metadatos y claves de archivos envueltas. El contenido cifrado vive en otro volumen y las claves maestras están separadas. Los metadatos también requieren protección y la exposición de una KEK cambia el alcance del incidente.

**¿Qué diferencia hay entre 401, 403 y 404?** 401 indica falta de una sesión válida. 403 indica una operación prohibida, por ejemplo un CSRF inválido. 404 puede indicar un recurso ausente o un documento cuya existencia se oculta al usuario sin acceso.

**¿Qué prueba demuestra que hay cifrado e integridad?** Recuperamos metadatos de un respaldo SQL, copiamos el archivo cifrado y usamos la KEK original. Obtuvimos los mismos bytes del TXT. Luego alteramos un byte de la copia y la verificación rechazó la descarga.

**¿Qué aporta Wireshark?** Permite observar el tráfico. En loopback registramos método, ruta y estado de solicitudes HTTP de salud sintéticas. La comprobación HTTPS validó el certificado y rechazó un host incorrecto. Eso demuestra controles concretos sin capturar credenciales.

**¿VLAN y WPA2 son lo mismo?** VLAN segmenta redes Ethernet mediante etiquetas 802.1Q. WPA2 protege el acceso inalámbrico. En el laboratorio virtual se verificó comunicación dentro de VLAN 10, aislamiento respecto a VLAN 20 y recuperación al reasignar el cliente. La asociación WPA2 en un AP aislado o simulador sigue pendiente de ejecución.

**¿Se puede considerar listo para producción?** La aplicación se verificó en un entorno local. El perfil HTTPS se probó con certificado temporal. Una entrega en otro equipo requiere certificado confiable para su hostname y la verificación correspondiente. La evidencia de CI publicada se vincula al commit que ejecutó el workflow.

**¿Qué hizo cada integrante?** Yuly preparó la interfaz y la integración con la API. Jacobo desarrolló autenticación, MFA, permisos, persistencia, cifrado y auditoría. Jerónimo preparó Docker, Nginx y CI/Trivy. El equipo documentó la validación de la integración y de los laboratorios locales.
